# Sysmon Configuration

Sysmon (System Monitor) is used in this lab to provide detailed endpoint telemetry from the Windows environment.

The configuration is focused on collecting useful behavioral information that can support security monitoring, detection engineering, and incident investigation.

Sysmon does not directly determine whether an activity is malicious. Instead, it records detailed endpoint activity that can later be analyzed by Wazuh and the analyst.

The active configuration is stored in:

```text
configs/sysmonconfig.xml
```

## Objectives

- Collect detailed Windows endpoint telemetry
- Monitor process creation and termination
- Monitor selected file activity
- Provide process and command-line context
- Monitor selected network activity
- Monitor selected registry activity
- Provide additional telemetry for security investigations
- Forward Sysmon telemetry to Wazuh
- Support incident investigation and timeline reconstruction

## Configuration Source

The Sysmon configuration used in this lab is based on the exported Sysmon configuration file and is stored in the repository as:

```text
configs/sysmonconfig.xml
```

The configuration defines which Sysmon event types are collected and what level of filtering is applied.

The goal is not to collect every possible event without consideration, but to provide useful telemetry for security monitoring while keeping the dataset practical for a home lab environment.

## Relevant Sysmon Events

The lab makes use of several Sysmon event types during investigation.

| Event ID | Event | Purpose |
|---|---|---|
| 1 | Process Create | Records process creation, command line, parent process, user, and related metadata |
| 3 | Network Connection | Records selected network connection activity |
| 5 | Process Terminate | Records process termination |
| 11 | File Create | Records file creation activity |
| 12 | Registry Event | Records registry object creation or deletion |
| 13 | Registry Value Set | Records registry value modification |

Not every event generated by Sysmon necessarily becomes a Wazuh alert.

Sysmon provides the telemetry, while Wazuh detection rules determine which events or combinations of events should be presented as security alerts.

## Process Monitoring

Process creation is one of the most important telemetry sources in this lab.

Sysmon Event ID 1 provides information such as:

```text
Image
CommandLine
ParentImage
ParentCommandLine
User
ProcessId
ParentProcessId
```

This information allows the analyst to reconstruct process relationships.

For example:

```text
explorer.exe
      │
      ▼
powershell.exe
      │
      ▼
normalfile2.exe
```

Process lineage can provide important context when determining whether an execution is expected or suspicious.

## File Monitoring

Sysmon Event ID 11 records file creation activity.

This is useful for detecting suspicious files being written to locations such as:

```text
C:\Users\<user>\AppData\Local\Temp\
```

One example from this lab is the creation of:

```text
normalfile2.exe
```

inside the user's temporary directory.

The event can then be correlated with subsequent process execution.

```text
File Created
     │
     ▼
Sysmon Event ID 11
     │
     ▼
Wazuh Detection
     │
     ▼
Process Execution
     │
     ▼
Sysmon Event ID 1
```

## PowerShell Monitoring

PowerShell activity is monitored primarily through process creation telemetry.

The command line provides important context for determining how PowerShell was executed.

For example:

```text
powershell.exe -EncodedCommand <BASE64_STRING>
```

The presence of `-EncodedCommand` can be used as an investigative indicator.

However, the existence of PowerShell or an encoded command alone does not prove malicious activity.

The analyst should correlate:

- Parent process
- User context
- Command line
- Decoded command
- Child processes
- File activity
- Network activity
- Timeline

## Network Monitoring

Selected network activity can be collected through Sysmon Event ID 3.

Network telemetry can provide additional context during an investigation.

For example:

```text
Process
   │
   ▼
Network Connection
   │
   ▼
Remote IP / Port
   │
   ▼
Correlation with Process Activity
```

Network events should be interpreted together with the originating process and surrounding activity.

## Registry Monitoring

Registry activity is collected through selected Sysmon registry events.

Relevant events include:

```text
Event ID 12
Event ID 13
```

Registry telemetry can provide additional evidence when investigating persistence mechanisms or configuration changes.

As with other telemetry sources, a registry event by itself does not automatically indicate malicious activity.

## Wazuh Integration

The Windows endpoint forwards Sysmon events through the Wazuh Agent.

The general flow is:

```text
Sysmon
   │
   ▼
Windows Event Channel
   │
   ▼
Wazuh Agent
   │
   ▼
Wazuh Manager
   │
   ▼
Detection Rules
   │
   ▼
Wazuh Alert
```

This integration allows Sysmon telemetry to be searched and correlated within the SIEM.

## Detection vs Telemetry

An important concept demonstrated throughout this lab is the difference between telemetry and detection.

```text
Sysmon Event
      │
      ▼
Telemetry Collected
      │
      ▼
Wazuh Analysis
      │
      ├── No matching rule
      │       │
      │       ▼
      │    Telemetry only
      │
      └── Matching rule
              │
              ▼
            Alert
```

For example, Sysmon Event ID 1 may record a process creation even when Wazuh does not generate a corresponding high-level alert.

This is expected behavior.

A SIEM should not necessarily generate an alert for every event because doing so would create excessive alert volume and reduce the analyst's ability to identify meaningful activity.

## Configuration Validation

After modifying the Sysmon configuration, the configuration should be validated before applying it to the endpoint.

The configuration should be tested to ensure that:

- The XML structure is valid
- Sysmon accepts the configuration
- The expected event types are enabled
- Filtering behaves as intended
- The endpoint continues generating the expected telemetry

Configuration validation is important because an invalid or overly restrictive configuration can reduce the visibility required for later investigations.

## Relationship with Incident Investigations

The Sysmon configuration directly supports several investigations in this repository.

### SMB Authentication Investigation

Windows authentication events are used to investigate repeated failed login attempts.

Sysmon provides additional endpoint context where applicable, while Windows Security Event 4625 provides the primary authentication telemetry.

### Benign PowerShell Investigation

Sysmon Event ID 1 records the PowerShell process creation.

Sysmon Event ID 11 records the temporary PowerShell execution policy test file.

These events can then be correlated with Wazuh alerts.

### Encoded PowerShell Investigation

Sysmon Event ID 1 provides the PowerShell command-line information required to identify:

```text
-EncodedCommand
```

This allows the analyst to investigate the command execution and correlate it with other endpoint activity.

### Temporary Executable Investigation

Sysmon Event ID 11 records the executable being created in the temporary directory.

Sysmon Event ID 1 records the subsequent execution.

Sysmon Event ID 5 records the process termination.

These events demonstrate how multiple telemetry sources can reconstruct an execution timeline.

## Lessons Learned

Sysmon provides detailed endpoint telemetry, but it does not replace a SIEM or detection engine.

The main lessons from this configuration are:

- Sysmon provides detailed Windows endpoint visibility.
- Process creation telemetry is particularly valuable for investigations.
- Parent-child process relationships provide important context.
- File creation events can reveal suspicious staging activity.
- Command-line information can significantly improve investigation quality.
- Network and registry telemetry can provide additional context.
- Not every Sysmon event should become a Wazuh alert.
- Detection rules determine which telemetry becomes analyst-facing alerts.
- Good detection depends on both telemetry quality and appropriate correlation.

## Current Scope

The current configuration is designed to support the security monitoring scenarios implemented in this lab.

It is not intended to represent a production enterprise Sysmon configuration.

Future improvements may include:

- Additional process filtering
- More precise network monitoring
- Improved registry monitoring
- Better noise reduction
- Detection-specific Sysmon rules
- Integration with additional endpoint telemetry
- Testing against additional attack simulations

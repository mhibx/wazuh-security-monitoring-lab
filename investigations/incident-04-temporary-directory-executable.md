# Incident 04 — Executable Dropped and Executed from Temp Directory

## Overview

This investigation examines a simulated scenario in which a Windows executable is copied into a user's temporary directory and subsequently executed.

The activity was intentionally reproduced using a benign copy of `notepad.exe`, renamed to `normalfile2.exe`. This allowed the behavior to be safely observed while still generating realistic Sysmon and Wazuh telemetry.

The investigation focuses on three related stages:

- Executable file creation
- Process execution
- Process termination

It also demonstrates an important distinction in security monitoring: **collected telemetry does not automatically become a SIEM alert**. Whether an event generates an alert depends on the detection rules applied to that telemetry.

---

## Objectives

- Simulate an executable being dropped into a temporary directory
- Observe Sysmon File Create telemetry
- Observe Sysmon Process Create telemetry
- Observe Sysmon Process Terminate telemetry
- Analyze the Wazuh alert generated by the activity
- Compare raw telemetry with generated alerts
- Understand how detection rules determine which events become analyst-facing alerts
- Identify opportunities for future event correlation

# Attack Simulation

The simulation uses the legitimate Windows Notepad executable as the test payload.

The original executable is:

~~~text
C:\Windows\System32\notepad.exe
~~~

It was copied into the user's temporary directory under a different filename:

~~~text
C:\Users\tempo\AppData\Local\Temp\normalfile2.exe
~~~

This creates a benign executable that exhibits a behavior commonly associated with malware staging: an executable is placed in a temporary directory and subsequently executed.

---

## Step 1 — Copy the Executable

~~~powershell
Copy-Item "$env:WINDIR\System32\notepad.exe" "$env:TEMP\normalfile2.exe"
~~~

The command creates:

# Investigation

## Why Did Event ID 11 Generate an Alert?

The executable was created inside:

~~~text
C:\Users\tempo\AppData\Local\Temp\
~~~

Temporary directories are commonly used by malware and other tools to stage files before execution.

The combination of:

- An executable file
- A temporary directory
- File creation through PowerShell

matched the conditions of Wazuh Rule 92213.

The rule therefore generated a high-level alert:

~~~text
Rule ID:
92213

Level:
15
~~~

This does not mean that the file itself was malicious. In this simulation, the executable was a legitimate copy of Windows Notepad.

---

## Why Did Event ID 1 Not Generate the Same Alert?

This experiment demonstrated an important distinction between **telemetry collection** and **detection**.

Sysmon generated Event ID 1 containing detailed information about the process creation:

~~~text
Image:
C:\Users\tempo\AppData\Local\Temp\normalfile2.exe

ParentImage:
C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe
~~~

Wazuh received this telemetry, but the existence of an event does not automatically mean that a high-level alert will be generated.

The event needs to match an applicable Wazuh detection rule.

The simplified flow is:

~~~text
Sysmon Event
     │
     ▼
Wazuh receives telemetry
     │
     ├── No matching detection rule
     │          │
     │          ▼
     │       No alert
     │
     └── Matching detection rule
                │
                ▼
              Alert
~~~

This is an important distinction when analyzing SIEM data.

---

# Important Finding

The investigation demonstrated that **not every piece of telemetry becomes an alert**.

| Activity | Sysmon | Wazuh Alert |
|----------|--------|-------------|
| Executable created in Temp | Event ID 11 | Yes — Rule 92213 |
| Executable executed | Event ID 1 | No equivalent high-level alert observed |
| Executable terminated | Event ID 5 | No equivalent high-level alert observed |

This behavior is expected in a detection system.

Creating an alert for every process creation or process termination event would generate significant noise. Detection engineering therefore focuses on identifying events and combinations of events that provide meaningful security context.

---

# Detection Engineering Perspective

A process creation event by itself is not necessarily suspicious.

For example:

~~~text
explorer.exe
    │
    ▼
notepad.exe
    │
    └── C:\Windows\System32\notepad.exe
~~~

would normally be consistent with legitimate user activity.

The scenario becomes more interesting when multiple behavioral indicators are combined:

~~~text
PowerShell
    │
    ├── Creates executable
    │
    ▼
%TEMP%\normalfile2.exe
    │
    ├── Executes executable
    │
    ▼
Process Create
~~~

A future custom detection could correlate these signals into a higher-confidence detection instead of relying on a single file-creation event.

For example:

~~~text
PowerShell
+
Executable created in a temporary directory
+
Same executable subsequently executed
~~~

could provide stronger evidence of suspicious activity.

The existing Wazuh alert mapped the detected behavior to:

| Field | Value |
|-------|-------|
| Technique | T1105 |
| Technique Name | Ingress Tool Transfer |
| Tactic | Command and Control |

The simulation itself was benign, so the ATT&CK mapping should be understood as the mapping associated with the **Wazuh detection rule**, rather than an assertion that the simulated activity constituted an actual instance of that technique.

The observed process execution and file staging behavior may also be relevant to other ATT&CK techniques depending on the surrounding context and detection logic.

# Lessons Learned

## 1. Telemetry Is Not the Same as an Alert

Sysmon can generate an event without Wazuh generating a corresponding alert.

~~~text
Telemetry ≠ Alert
~~~

Raw telemetry provides the evidence. Detection rules determine which patterns are promoted into alerts.

---

## 2. Detection Rules Determine What Becomes Interesting

Wazuh's detection rules act as a layer between raw endpoint telemetry and analyst-facing alerts.

This allows the SIEM to focus analyst attention on events that match known security-relevant patterns.

---

## 3. Context Matters

An executable running from a trusted Windows directory is very different from an executable appearing in:

~~~text
%TEMP%
~~~

and being launched by:

~~~text
PowerShell
~~~

The surrounding process lineage and file location provide important context for the investigation.

---

## 4. Timeline Analysis Is Important

Initial searches did not always immediately reveal the expected Event ID 1 and Event ID 5 records.

Using an absolute time range around the known execution timestamp made the events easier to locate.

This reinforced the importance of timeline-based investigation rather than relying exclusively on keyword searches.

---

## 5. Alert Noise Must Be Controlled

A SOC should not necessarily create an alert for every process creation event.

Instead, detection engineering should focus on high-value behavioral combinations that provide enough context to justify analyst attention.

# Conclusion

This investigation demonstrated the behavior of an executable being staged in a temporary directory and subsequently executed through PowerShell.

The most important result was not simply that Wazuh generated an alert, but that the investigation exposed the relationship between:

~~~text
Telemetry
    ↓
Detection Rule
    ↓
Alert
    ↓
Analyst Investigation
~~~

The executable creation triggered Wazuh Rule 92213, while the subsequent process creation and termination were available as telemetry without producing an equivalent high-level alert.

Because the executable was a renamed copy of the legitimate Windows Notepad binary, the scenario also demonstrated why automated detections require analyst validation. The observed behavior matched a suspicious pattern, but the underlying activity was intentionally benign.

This provides a practical foundation for the next stage of the lab: **event correlation and custom detection engineering**, where multiple low-level events can be combined into a higher-confidence security detection.

---

# SOC Takeaway

A security alert should be treated as a starting point for investigation rather than a final verdict.

In this case, an executable created in `%TEMP%` and executed through PowerShell was enough to trigger a detection. However, examining the process lineage, file metadata, timeline, and subsequent telemetry showed that the executable was actually a renamed copy of legitimate Windows Notepad.

Effective SOC analysis therefore requires both **automated detection and human-driven contextual investigation**.
